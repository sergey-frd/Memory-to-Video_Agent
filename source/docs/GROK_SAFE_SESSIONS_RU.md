# Grok: безопасные сессии и диагностика загрузки

Проверено 2026-09-29 для корневого `run_full_grok_pipeline.bat` →
`main_full_pipeline.py` → `main_grok_batch.py` → `api/grok_web.py`.

```bat
run_full_grok_pipeline.bat --config-file .\config_BnMx.json --upload-timeout 300
```

## Исправленная потеря данных

Ранее main_full_pipeline очищал весь settings.output_dir перед изображением,
после успеха и в обработчике ошибки. main_grok_batch также очищал общие input/output.
Эти очистки удалены из обоих обработчиков.

Теперь каждое изображение имеет изолированную рабочую сессию:
`output/.grok-sessions/<sha256>/work/` и соседний `state.json`.
Ключ учитывает путь и содержимое изображения, конфигурацию и параметры моделей.
Одинаковый запуск находит прежнюю сессию, даже если очередь стала короче.
Передача исходного изображения в batch явная: имя stage больше не определяет исходник.

После подготовки промпты сохраняются для повторного запуска. Для успешно
полученного ролика batch записывает `.mp4.complete.json` с хешами ролика,
промпта и исходника. При повторной попытке подтверждённые ролики пропускаются;
одного наличия файла MP4 недостаточно. Старые ролики без этих записей автоматически
не считаются результатами новой сессии.

После завершения всех вариантов изображения результаты копируются в final_videos_dir,
проверяется равенство SHA-256 оригинала и доставленной копии, вспомогательные файлы
сохраняются в regeneration_assets_dir. Затем очищается только work этой сессии.
Маленький state.json остаётся: он позволяет пропустить повторно добавленный исходник,
пока конечные результаты существуют и совпадают по хешу. Изменение конфигурации
создаёт другую сессию. Хеш подтверждает целостность доставки, не художественное
качество и не корректность декодирования видео.

Исходник удаляется из очереди input только после успешной доставки. Внешний исходник
не удаляется. При ошибке input и work сохраняются; отчёт находится в error/output.
continue_after_failure управляет переходом к следующему изображению. Для повтора
достаточно той же команды. --no-submit сохраняет исходники и промежуточные файлы.
Отдельный main_grok_batch больше не удаляет общие input/output; --keep-workdirs
сохранён для совместимости. Одновременный запуск одной и той же очереди не поддерживается.

Это исправление относится к корневому браузерному workflow. Отдельные API/desktop
исполнители и копия дистрибутива source/ этим изменением не мигрированы.

## Почему мог отправляться только текст

Загрузка уже использовала Playwright set_input_files, а не поиск Windows-окна
по координатам. Но проверка готовности принимала доступную кнопку отправки,
любую картинку страницы и даже наличие кнопки по истечении таймаута за успех.
Это позволяло отправить текст при отсутствующем вложении.

Теперь файл передаётся абсолютным путём; предпочтение отдаётся image file-input.
Перед загрузкой запоминаются существующие картинки. Для отправки требуется новое
загруженное изображение в области формы/вложений и два спокойных опроса без загрузки.
Кнопка отправки или имя файла сами по себе не подтверждают вложение. При таймауте
генерация останавливается, сохраняются screenshot/HTML/JSON для диагностики.
Новый селектор требует проверки на действующей странице Grok: при изменении DOM
он может безопасно остановиться вместо отправки. Live-проверка загрузки и получения
MP4 в рамках исправления не выполнялась; работоспособность сайта не объявляется подтверждённой.

## Codex и существующая классификация BM26

Встроенный браузер приложения позволяет агенту взаимодействовать со страницей
внутри приложения. Это отдельный способ работы агента, а не автоматически доступный
Python/BAT транспорт. Подключение такого процесса требует отдельного маршрута
с очередью, проверкой вложения и фиксацией скачанных результатов.
Официальная документация: https://learn.chatgpt.com/docs/browser?surface=app

main.py уже строит промпты на основе SceneAnalysis: содержание сцены, число людей,
композиция, действие, атмосфера и отношения. Но _run_generation при новой подготовке
вызывает анализатор заново. Автоматический импорт classification_result.json BM26
в этот workflow пока не реализован. Нужна явная привязка записи классификации к
конкретному исходнику; предпочтительно проверять путь и хеш, а не только имя.
Codex может подготовить индивидуальные промпты по существующим записям и задаче фильма.

Пример общего ограничения для семейного BM26 (не индивидуальный промпт по проверенной карточке):

> Animate the supplied photograph as one continuous, restrained family-memory shot.
> Preserve every person's identity, age, facial proportions, hairstyle, clothing,
> body position and the original composition. Use only subtle breathing and a very
> slow camera push-in. Keep hands and facial expressions stable. Preserve the exact
> number of people and all background objects. No head turns, walking, speaking,
> invented gestures, new objects, face morphing or scene changes. Convey warmth
> through gentle motion while retaining the original lighting and colors.

Если на фото нет людей, эти ограничения заменяются предметными. Если карточка
не подтверждает личности, не следует угадывать, кто Беня и кто Макси. Ограниченный
промпт снижает риск искажений, но не гарантирует их отсутствие: нужен просмотр MP4.
В config_BnMx включены оптимальное/identity-safe кадрирование 70% и скрытие телефона;
это допускает изменения исходной композиции. Для строго бережного режима их нужно
осознанно пересмотреть, а не считать текущую конфигурацию автоматически минимальной.

## Журнал завершённых изображений на время работы

`output/.grok-completed/<проект>/<sha256 изображения>.json` сохраняется между
повторными попытками и после отдельных успешных элементов очереди.
Проект определяется конечным каталогом final_videos_dir. Проверяются наличие и
SHA-256 всех записанных результатов. Совпадающее изображение пропускается даже
под другим именем и в другом списке. Изменение настроек само по себе не отменяет
завершение; для намеренной новой версии используйте `--force-regenerate`.
Результаты, сделанные вне скрипта, нужно явно зарегистрировать после проверки
доставки (record_completed); автоматического поиска совпадений по имени MP4 нет.
Успешные исходники удаляются из input при завершении прохода по очереди;
неуспешные остаются. Пустая очередь завершается успешно без запуска генерации.
Рабочие папки отдельных успешных изображений очищаются после доставки,
общий output этим workflow не очищается. При полном закрытии проекта записи
реестра и относящийся к очереди кэш можно удалить отдельной точечной очисткой
после проверки архива: [порядок закрытия](GROK_QUEUE_RU.md#очистка-после-полного-закрытия-проекта).
Исторический архив не подгружается автоматически, поэтому после закрытия
повторная ручная подача той же фотографии может создать новое видео.


## Очередь с проверенными промптами BM26

Для партии 10 исходников 2026-09-29 используется:

```powershell
python scripts/run_grok_prepared_queue.py output/BM26_GROK_QUEUE_20260929/plan.json
```

План содержит SHA-256 каждого входного изображения, соответствующую карточку
классификации BM26 и индивидуальный промпт, подготовленный агентом после
визуальной проверки. Исполнитель не вызывает повторную классификацию и не
генерирует дополнительные варианты: один исходник — один ролик 6 секунд,
720p, без звука, с сохранением пропорций исходного фото.

Перед каждым исходником исполнитель возвращает существующую вкладку Chrome
с порта 9222 на /imagine, проверяет пустое вложение и настройки, затем загружает
изображение через input[name=files]. Готовность подтверждается кнопкой удаления
вложения и загруженной миниатюрой. После последнего ролика вкладка также
возвращается на чистую форму; плеер предыдущего видео не остаётся в цикле.

После отправки сохраняется URL результата. При возобновлении SUBMITTED
используется тот же результат без новой генерации. Неоднозначный SUBMITTING
требует проверки и не отправляется повторно автоматически. Доставленные файлы
проверяются декодированием и SHA-256; source-копия сохраняется в архиве проекта.
В конце прохода удаляются только подтверждённые успешные исходники из input
и проверенные рабочие дубликаты MP4. Неуспешные исходники и состояния сохраняются.
Постоянный журнал .grok-completed предотвращает повторную генерацию в новых списках.
План и маленькие состояния очереди сохраняются для аудита и восстановления.
