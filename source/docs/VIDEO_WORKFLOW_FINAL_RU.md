# Технология видео: полный сценарий, редакции и финальный экспорт

## Актуальное продолжение технологии

Для завершения FULL / MINIMAL и хранения результатов используйте [актуальное руководство](FULL_MINIMAL_PRODUCTION_RU.md). Нижеследующие этапы описывают подготовку и альтернативы; старый short не является основой нового MINIMAL.

Единая точка запуска — `run_video_workflow.bat`, исполнитель — `tools/run_video_workflow.py`.
Это параметризованный сценарий с сохранением состояния, а не один непрерывный рендер.
Он объединяет существующие batch/Python-этапы и останавливается для просмотра черновика
и для операций, которые выполняются внутри Premiere. Под «скриптами» здесь понимаются
программы автоматизации, а не расшифровка речи.

## Порядок работы

1. Инвентаризация файлов исходной sequence, превью и контактные листы.
2. Классификация материалов, по умолчанию с ИИ.
3. Создание сразу компактной структуры: порядок и индивидуально достаточные длительности без заполнения лишних секунд. См. [правило первой сборки и его реализацию](COMPACT_FIRST_RU.md).
4. Монтажный план с конкретными IN/OUT и MP4 720p для просмотра.
5. Остановка. Критика черновика с тайм-кодами и создание альтернативного MP4 720p на той же классификации. Сравнение вариантов, выбор и при необходимости дальнейшие редакции.
6. Явное утверждение выбранного черновика.
7. Подготовка копии проекта Premiere, сборка утверждённого плана и экспорт 1080p.
8. Анимация фотографий в следующей копии проекта и нативный экспорт.
9. Переходы между подходящими видео в следующей копии и нативный экспорт.
10. Индивидуальная цветокоррекция и общий цветовой стиль; сравнительная проба и утверждение цвета (подготовка и JSX реализованы; нативное применение требует проверки).
11. Нативный экспорт с утверждённым цветом, просмотр и приёмка.
12. Архивирование и очистка после приёмки.

**Граница реализации:** `finish` теперь поддерживает цвет после переходов при `color.enabled: true`.
Старые конфигурации без `color` пропускают его с явной отметкой. Подготовка JSX не означает
применение цвета; итоговый MP4 и лица нужно проверить перед `accept`.

Классификация не запускается заново при изменении IN/OUT или создании альтернативы.
Точные редакции командой `revise` не используют ИИ:
они применяют конкретные решения монтажёра. 720p собирается из исходных файлов;
1080p также использует оригиналы, а не увеличивает готовый черновик.

## Конфигурация нового героя

Скопировать `config_workflow.example.json` в `config_workflow_Имя.local.json`.
Заполнить `config_pipeline_Имя.local.json` по `config_pipeline.example.json`:
описание героя, Premiere-проект, исходная sequence, пустая целевая sequence,
длительность, модель ИИ и сюжетное задание.

| Поле общей конфигурации | Значение |
|---|---|
| `schema_version` | `1` |
| `output_root` | Отдельная папка состояния сценария для героя |
| `pipeline_config` | Конфигурация инвентаризации → классификации → структуры → 720p |
| `native.project` | Исходный проект с пустой целевой sequence |
| `native.target_sequence` | Имя целевой sequence |
| `native.preset` | Установленный Premiere `.epr`; использован Match Source - High bitrate |
| `animation.enabled`, `transitions.enabled` | Включение этапов, по умолчанию `true` |
| `animation.peak_fraction` | Доля длительности до максимума увеличения, по умолчанию `0.58` |
| `animation.zoom_fraction` | Относительное увеличение Scale, по умолчанию `0.14` |
| `animation.return_fraction` | Доля обратного движения, по умолчанию `0.18` |
| `transitions.duration_seconds` | Длительность Cross Dissolve, по умолчанию `0.4` |
| `transitions.minimum_clip_seconds` | Минимум для каждого из двух соседних видео, по умолчанию `8` |
| `initial_review_result` | Необязательно: существующий `render_result.json` вместо запуска первых этапов |
| `initial_review_video` | Необязательно: новое имя перемещённого/переименованного черновика; SHA256 должен совпадать с отчётом |
| `existing_jobs` | Необязательно: готовые `native`, `animation`, `transitions` job.json для подключения существующей работы |

Все пути конфигурации разрешаются относительно её папки. `existing_jobs` применяется
только к первоначальному подключённому черновику, не к последующим редакциям.
Нативный проект, sequence и preset должны соответствовать настройкам проекта в pipeline.
Для обычной новой задачи поля `initial_review_result` и `existing_jobs` не нужны.

ИИ включён по умолчанию в конфигурации pipeline (`ai_enabled: true`). При выключении
ИИ начальные этапы могут остановиться для ручной подготовки данных: автоматического
равноценного анализа без ИИ сценарий не обещает. Контроль структуры и личности героя
остаётся необходимым независимо от режима ИИ.

## Первый запуск до низкого разрешения

Запускать из корня проекта в CMD:

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action start
```

Сценарий выполнит начальный pipeline до черновика, напечатает путь к видео и остановится
со статусом `REVIEW_REQUIRED`. Повторный `start` покажет уже готовое видео после проверки
его контрольных сумм. Начальный pipeline имеет собственные checkpoint и логи.
При `UPSTREAM_REVIEW_REQUIRED` сначала требуется устранить проблему/заполнить ручные данные
соответствующего начального этапа; готовый черновик в этом случае не заявляется.

Для проверки исходной конфигурации без API и рендера:

```bat
run_hero_pipeline.bat config_pipeline_Имя.local.json --check
```

## Итерации монтажного плана

### Критика и альтернативное видео на той же классификации

После первого MP4 720p нужно оценить начало и финал, ясность истории, присутствие
героя, темп, повторы, смену крупности и визуальные стыки. Замечания должны содержать
тайм-код, наблюдение и конкретное предложение, а также отмечать удачные решения.
На основании критики создаётся самостоятельный вариант B: допускаются другой набор
материалов из прежнего каталога, порядок, группировка и длительности. Классификация
и исходный вариант A сохраняются; классификатор повторно не запускается.

Исполнитель `tools/review_draft_alternative.py` извлекает из готового MP4 три кадра
каждого плана, передаёт их с тайм-кодами, монтажным планом и прежним каталогом модели
из конфигурации. Это визуальная выборка, а не просмотр непрерывного видео со звуком:
речь, музыка, точность действий и стыков требуют отдельного просмотра. Максимум —
80 планов за один анализ. API-запрос содержит выбранные кадры и данные каталога.

Скопируйте `config_alternative.example.json` в конфигурацию героя. Укажите результат
**той же** классификации, сюжетное задание, длительность, модель и обязательные/
исключённые ID. Пути разрешаются относительно этой конфигурации.

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action alternative --alternative-config config_alternative_Имя.local.json
```

Команда создаёт `CRITIQUE_RU.md`, `critique_and_alternative.json`, новый монтажный
план и второй MP4 720p из оригинальных медиа. Замечания должны ссылаться на реальные
тайм-коды выборки; альтернатива обязана отличаться монтажом, а не только названием.
Результат — `ALTERNATIVE_REVIEW_REQUIRED`, не автоматическое утверждение. Ошибка
рендера допускает повтор той же команды с сохранённой критикой без нового API-запроса.

Просмотрите оба видео и выберите вариант (номера соответствуют порядку `reviews`
в `workflow_state.json`, начиная с 1):

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action select --review-index 1
run_video_workflow.bat config_workflow_Имя.local.json --action approve
```

Для альтернативы используйте `--review-index 2`. Можно выбрать исходный вариант;
создание альтернативы не означает, что он хуже. После выбора `revise`, `approve`
и `finish` работают с выбранной версией. Выбор и новые редакции снимают прежнее
утверждение. Оба видео и критика сохраняются для сравнения.

В новом образце workflow включено `review.require_alternative: true`: без готовой
альтернативы утверждение запрещено. Старые конфигурации без этого поля совместимы
с прежним сценарием; действие `alternative` доступно и для них. Не меняйте уже
запущенный конфиг ради добавления поля — это нарушит его контрольную сумму.

### Повторные итерации с критикой результата

Цикл: **DRAFT → CRITIQUE → ALTERNATIVE → CRITIQUE → ALTERNATIVE…**.
Общее монтажное правило: **не держать два длинных эпизода одинаковой эмоциональной
энергии подряд без драматургической причины**. Причина фиксируется в обосновании
выбора сцен. Энергия оценивается по действию и контексту; неизвестное не додумывается.
Для устранения плато можно разнести спокойные сцены либо вставить между ними
короткий активный эпизод из прежней классификации. Семейная теплота сохраняется.
Сокращение хронометража само по себе не считается улучшением. Правило применяется
при построении структуры, критике альтернативы и сравнении после рендера; это
редакторский критерий, а не автоматическое определение эмоций по длине клипа.
Критика рассматривает соответствие темпа известному характеру героя, монотонность,
затянутость и повторы; предлагает сокращения, перестановки и замены, оценивает
визуальное разнообразие и контраст, а также использование сильных материалов
из полного прежнего каталога. Неизвестные черты героя не додумываются.

Простая перестановка тех же клипов с теми же длительностями отклоняется валидатором.
Нужны изменения выбора материалов, длительностей или исходных диапазонов,
обоснованные найденными недостатками. Различие монтажа само по себе не доказывает
улучшение: после рендера отдельный вызов модели сравнивает кадры обоих MP4 и планы.

Каждый запуск `--action alternative` создаёт **одну** новую итерацию, включая её
повторную критику. Следующий запуск той же команды продолжает от выбранной версии
и получает замечания предыдущей оценки. Каталог не классифицируется повторно.
Папки `alternative_2`, `alternative_3` и далее сохраняются отдельно. Возобновление
прерванного запуска использует ту же папку; готовые предыдущие версии не заменяются.

Для каждой новой версии сохраняются `POST_CRITIQUE.json` и `ITERATION_REPORT_RU.md`:

1. Обнаруженные недостатки.
2. Внесённые изменения.
3. Обоснование и наблюдаемый эффект изменений.
4. Нерешённые проблемы.

Следующая итерация разрешается, если повторная оценка показывает заметное улучшение
и называет конкретные оставшиеся исправимые недостатки. При плато, ухудшении или
неуверенности — остановка `ITERATION_REVIEW_REQUIRED`: нужно сравнить сохранённые
версии и выбрать подходящую через `select`. Оценка модели предварительная;
автоматического утверждения видео нет. Сравниваются выборки кадров и длительности,
а не непрерывный видеоряд и звук; полноценный просмотр остаётся необходимым.

### COMPARE → BEST ASSEMBLY

После сравнения нескольких альтернатив можно выбрать лучшие решения **по частям**,
а не утверждать один ролик целиком. `tools/build_best_assembly.py` восстанавливает
фрагменты из монтажных планов и оригинальных медиа; готовые черновики не склеиваются.

Конфигурация содержит `schema_version: 1`, новую `output_dir`, `model`, `narrative`,
список выводов `comparison` и `selections`: для каждого фрагмента — `review_index`
(нумерация reviews с 1), `in_seconds`, `out_seconds` по шкале выбранной версии,
`reason`. Порядок selections задаёт новый монтаж. Границы должны попадать на кадры;
повторные материалы и смешанные fps отклоняются. Выбор фрагментов редакторский,
скрипт не считает одну версию автоматически лучшей.

```bat
run_video_workflow.bat config_workflow_Ben26.local.json --action best-assembly --assembly-config config_best_assembly_Ben26.local.json
```

Сохраняются карта происхождения фрагментов, отдельный edit_plan, MP4 720p и
`BEST_ASSEMBLY_RU.md`; повторная критика сравнивает сборку с выбранной до запуска
версией. Предыдущие версии не меняются. Статус `BEST_ASSEMBLY_REVIEW_REQUIRED`
требует просмотра; дальнейшие approve/finish работают с этой сборкой.
После сбоя повтор той же команды продолжает незавершённую сборку. Для другой
сборки используйте новый конфиг и выходную папку. Автоматического утверждения нет.

### Точные ручные редакции

Смотреть выбранное видео, указанное командой `start`, `alternative` или `revise`.
Путь к последнему `edit_plan.json` находится в `workflow_state.json`, в последнем
элементе `reviews` при обычных редакциях. После `select` используется элемент с
индексом `selected_review` (индекс в JSON начинается с нуля). Состояние печатает `status`.

Создать отдельный JSON редакции, например:

```json
{
  "schema_version": 1,
  "revision": "v2",
  "source_edit_plan": "output/Имя/workflow/draft_run/edit_plan.json",
  "output_dir": "output/Имя/revisions/v2",
  "timeline_ranges": [
    {"in_seconds": 0, "out_seconds": 9, "note": "Сократить вступление"},
    {"in_seconds": 13, "out_seconds": 22, "note": "Оставить взаимодействие"}
  ]
}
```

Путь `source_edit_plan` в примере условный: заменить на фактический путь из состояния.
`timeline_ranges` — **полный список сохраняемых частей последнего черновика**.
Всё, чего нет в списке, исключается. Это позиции во входном черновике, не тайм-коды V1
после перехода к V2 и не позиции в файлах камеры. IN включается, OUT исключается.
Интервалы идут по возрастанию, не пересекаются и совпадают с сеткой кадров.
Можно сохранить две части одного исходника: исполнитель сам рассчитает новые IN/OUT.
Альтернатива — режим `clips` с явными ID и исходными IN/OUT; режимы взаимоисключающие.

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action revise --revision-config config_revision_Имя_v2.local.json
```

Команда создаёт новую редакцию, рендерит её в 720p и снова останавливается для просмотра.
Для следующей итерации использовать следующий номер, новую `output_dir` и последний план.
Редакция создаётся без перезаписи предыдущих файлов. После прерванного рендера повторить
ту же команду с той же конфигурацией: уже записанный план используется повторно.
Незавершённую редакцию нужно завершить до утверждения/финализации.

## Утверждение монтажа

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action approve
```

Эта команда означает, что пользователь просмотрел и одобрил **выбранный** черновик
(по умолчанию — последний, если другая версия не выбрана командой `select`).
Фиксируются контрольные суммы плана и видео. Новый `revise` снимает утверждение и
сохраняет предыдущую цепочку финализации в истории; файлы не удаляются.

## Продолжение до финала

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action finish
```

Сценарий дойдёт до первой невыполненной операции Premiere и напечатает:

- точный путь к копии `.prproj`, которую нужно открыть;
- точный путь к JSX, который нужно запустить через **Window → Extensions → Run Transition Script**;
- статус `WAITING_PREMIERE_NATIVE`, `WAITING_PREMIERE_ANIMATION` или `WAITING_PREMIERE_TRANSITIONS`.

После выполнения JSX повторить **ту же команду `finish`**. Сценарий проверит журнал
успешного экспорта и полное декодирование MP4, затем подготовит следующий этап.
Он не управляет интерфейсом Premiere и не выдаёт подготовку JSX за выполненный рендер.
При ошибке JSX посмотреть `native_progress.log` и `native_status.txt`; повторный запуск
сборки на частично заполненной sequence запрещён. Исправление такого сбоя — отдельная
операция, не автоматическая очистка пользовательского монтажа.

Для остановки на промежуточном результате:

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action finish --until native
run_video_workflow.bat config_workflow_Имя.local.json --action finish --until animation
```

Без `--until` финиш включает анимацию, переходы и включённый в конфигурации цвет. Сценарий не меняет длительности клипов
на этих этапах. Анимация относится к фотографиям. Переходы создаются только на подходящих
стыках; при отсутствии фотографий или подходящих переходов общий сценарий
пропускает этап с явной причиной. Можно отключить этап через `enabled: false`.
Самостоятельные исполнители при пустом наборе останавливаются с ошибкой.

`FINAL_REVIEW_REQUIRED` означает: все включённые нативные экспорты технически проверены,
но художественная оценка ещё не выполнена. Просмотреть картинку, лица, движение,
стыки, звук и финальную фотографию. Затем:

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action accept
```

Только эта команда устанавливает `FINAL_ACCEPTED`. Она не публикует видео, не отправляет
его на Google Drive/GitHub и не удаляет исходники или временные результаты.

## Возобновление и защита результатов

```bat
run_video_workflow.bat config_workflow_Имя.local.json --action status
```

Состояние: `output_root/workflow_state.json`; общий лог: `workflow.log`;
в папках этапов — подробные журналы обработки и FFmpeg/Premiere.
Для проверенного завершённого этапа сверяются контрольные суммы, повторного рендера нет.

## Последний этап: хранение и очистка — closeout

После просмотра финального видео, `accept` и закрытия рабочей копии Premiere:

```bat
REM Составить план размещения и удаления — без переноса и удаления
run_video_workflow.bat config_workflow_Ben26.local.json --action closeout --closeout-config config_workflow_closeout_Ben26.local.json

REM Архивировать, проверить контрольные суммы, затем очистить рабочую папку
run_video_workflow.bat config_workflow_Ben26.local.json --action closeout --closeout-config config_workflow_closeout_Ben26.local.json --apply
```

`--apply` относится только к closeout. Без него составляется план; без `FINAL_ACCEPTED`
даже перенос не начинается. Общая конфигурация workflow не меняется, поэтому её
контрольная сумма и предыдущие checkpoint остаются действительными.

Для нового героя использовать `config_workflow_closeout.example.json`.
`task_id` — имя папки под repository/output, например Ben26 или Arkady26;
`working_dir` обязан точно соответствовать output/task_id. `hero_config` указывает
конфигурацию мест хранения. `report_dir` должен находиться вне очищаемой папки.
`project_scan_roots` — все места, где могут храниться проекты, ссылающиеся на рабочие файлы.
`video_config_key` и `project_config_key` выбирают поля конфигурации героя.

Размещение по умолчанию:

| Что сохраняется | Место из конфигурации героя |
|---|---|
| Финальный MP4 | `final_videos_dir/<task_id>/final/` |
| Финальный редактируемый проект | `premiere_project_dir/<task_id>/final/` |
| Классификация и её история | `source_materials_dir/classification/<task_id>/final_archive/` |
| Планы, черновики, промежуточные проекты, отчёты | `regeneration_assets_dir/<task_id>/final_archive/history/` |
| Исходные байты преобразованных JSON/проектов, конфигурации и снимок кода | `regeneration_assets_dir/<task_id>/final_archive/provenance/` |
| Манифест и карта перемещения | `regeneration_assets_dir/<task_id>/final_archive/metadata/` |

Для Ben26 финальный MP4 попадёт в
`<LOCAL_PATH>`,
проект — в `<LOCAL_PATH>`.

Перенос реализован как копирование, проверка SHA256, затем удаление рабочей копии.
Существующий отличающийся файл в месте назначения не перезаписывается. Пути зависимостей
в архивных проектах и JSON переназначаются; исходные байты сохраняются отдельно.
Неизменность остальных данных проекта проверяется. Нативное открытие перемещённого
проекта отдельно не считается выполненным: для будущего редактирования открыть его
в Premiere и проверить доступность медиа.

Удаляются только перечисленные в плане файлы внутри папки этой задачи. Сегменты FFmpeg
`segments/*.mp4`, кэш `.prin/.pek/.cfa/.pyc/.tmp` и звуковые превью не архивируются,
если не требуются сохранённым проектам. Финальные файлы, исходные фото/видео, семейные
описания и код рабочего репозитория не удаляются. Черновики и промежуточные проекты
сохраняются в истории для восстановления, но освобождают рабочую папку.

Перед удалением повторно проверяются архив, финальные копии и ссылки внешних проектов.
Новые или изменённые рабочие файлы останавливают очистку. Файлы, нужные внешним проектам,
остаются на месте и перечисляются в отчёте. Поэтому статус CLOSED не означает, что
рабочая папка обязательно пуста: у неё могут остаться защищённые зависимости.

После прерывания повторить ту же команду с `--apply`: сохранённый внешний журнал
`cleanup_pending.json` позволяет продолжить даже после удаления рабочего state-файла.
После завершения повторная команда проверяет архив и итоговые файлы. Результат:
`report_dir/closed.json`, журнал удалений и контрольные суммы; копия итогового отчёта
сохраняется также в постоянном хранилище. Старые checkpoint workflow после очистки
являются историей, а не рабочим сценарием возобновления. Для новой редакции восстановить
отдельную рабочую папку из архива.

Этап реализован и проверен на тестовых данных. Очистка реальных файлов Ben26 пока
не запускалась: финальная приёмка в общем workflow ещё не зарегистрирована.


## Цвет: индивидуальная коррекция и единый стиль фильма

Реализованы `tools/prepare_plan_color.py` и `run_prepare_plan_color.bat`.
Рабочий шаблон — `config_color.example.json`; прежний `config_color_design.example.json`
сохранён как историческая спецификация, а не исполняемый файл.

```bat
run_prepare_plan_color.bat config_color_Ben26_v3.local.json --dry-run
run_prepare_plan_color.bat config_color_Ben26_v3.local.json
```

Открыть выведенную копию COLOR_REVIEW.prproj и выполнить color_export.jsx в Premiere.
Он добавляет два Lumetri на каждый фрагмент: первый для индивидуальной коррекции,
второй для единого стиля, сохраняет редактируемый проект и экспортирует color_1080p_review.mp4.
Параметры считываются после записи; при несовместимости API/названий параметров экспорт
останавливается. Уже существующий Lumetri запрещён для защиты от накопления коррекций.
Скрипт использует английские названия Basic Correction; первая Saturation — базовая,
её нейтральное значение проверяется. QE и Lumetri требуют нативного теста на установленном Premiere.

### Конфигурация и художественная цель

`source_job` — задание предыдущего этапа, `output_root` — новая папка запусков.
`creative_brief` содержит `purpose`, `mood`, `lighting_intent`, `music_direction`, `references`.
Эти поля фиксируют замысел человека; скрипт не делает семантический анализ песни или референсов.
Задача профиля — поддержать цель фильма, сохраняя естественные лица и свет сцены.

`global_look.profile`: neutral, warm_family, bright_optimistic или quiet_reflective.
Это пробные авторские направления, не объективное соответствие эмоции одному цвету.
`strength` от 0 до 1 смешивает параметры с нейтральными; `overrides` переопределяет профиль.
Temperature, Tint, Exposure, Contrast, Highlights, Shadows, Whites, Blacks, Saturation
можно задавать явно в допустимых консервативных пределах. Общий слой одинаков на всех клипах,
индивидуальные поправки остаются независимыми. Изменение профиля требует новой копии от
проекта до цвета, чтобы не накладывать коррекцию повторно.

`individual.exposure_mode`: suggest (только предложения), apply_conservative (применить
ограниченное выравнивание яркости), manual (только ручные поправки).
`maximum_auto_exposure` от 0 до 0.3 ступени. `overrides` — словарь по clip_instance_id,
который берётся из color_plan.json. Ручные значения заменяют автоматические.
Для видео анализируются 20%, 50%, 80% диапазона; фотография анализируется один раз.
Из средней яркости уменьшенных кадров вычисляется ограниченная поправка относительно
медианы фильма. Это эвристика яркости, не измерение экспозиции, не определение баланса
белого и не анализ кожи. Цветовое пространство/HDR и сложное освещение проверяются вручную.
Постоянная поправка для каждого фрагмента не создаёт покадровых скачков настроек.

### Ben26 и проверка

Пробный профиль: warm_family 35%, максимум поправки экспозиции ±0.2 ступени.
Цель: тёплая семейная история взросления, любопытства и близости, без сильного цветового фильтра.
Это предложение для просмотра, не утверждённый стиль. Музыка не анализировалась.
Созданы исходные кадры-пробы, color_plan.json и color_job.json с отдельными параметрами
двух слоёв. Монтаж и ссылки на оригиналы прошли dry-run. Применение Lumetri и нативный
экспорт ещё ожидают запуска JSX. Проверить лица, света, тени, стыки и переходы, сравнив
с предыдущим MP4; при необходимости изменить overrides и подготовить следующую копию.
Нативная цветовая проба сейчас экспортируется в 1080p; автоматической A/B-композиции
и отдельного цветового 720p этот исполнитель пока не создаёт.

### Общий сценарий

В конфигурации workflow раздел `color` содержит поля цветовой конфигурации кроме
schema_version, source_job, output_root; `enabled: true` включает этап после transitions.
`finish --until color` (по умолчанию) готовит цвет и останавливается в WAITING_PREMIERE_COLOR.
После JSX повторить finish, просмотреть цветовой результат и только затем accept/closeout.
Closeout сохраняет именно цветовой MP4 и проект, когда этап выполнен.
Для Ben26 создан отдельный config_workflow_Ben26_color.local.json, чтобы не менять
контрольную сумму ранее зарегистрированной конфигурации. Он подключает готовые задания.
Если старый проект сохранён позже старого MP4, общий сценарий по-прежнему потребует свежий экспорт.

## Уточнение 22.09.2026: первые FULL и SHORT

FULL — до 360 секунд или меньше, без нижней квоты. SHORT — самостоятельный портрет 60–180 секунд из фактического FULL edit-plan, доступен сразу после готовности плана, без ожидания FULL MP4, FULL_LOCK или просмотра. Сначала оба черновика, затем общая критика и итерация.
Для обеих версий: не удерживать кадр после того, как смысл понятен, если новых деталей/действий не появляется; не растягивать вступления и пары оригинал–ART ради хронометража. Выразительные паузы обосновывать содержанием, не механически ускорять все кадры.
Универсальные запуски: run_portrait_draft.bat CONFIG [--check] и run_short_portrait.bat CONFIG [--check]. Проверка не вызывает AI и не рендерит. SHORT использует только ID из FULL, не удлиняет кадры, сохраняет исходные медиа и границы видеоматериала. FULL и SHORT пишут в отдельные папки. Исходное аудио только там, где оно есть; фото беззвучны, новая музыка/TTS не добавляются.
Для HEIC требуется pillow-heif>=1.0 в том Python-окружении, которым запускается BAT. Наличие пакета в другом Python недостаточно.

## Опции отдельного задания: coverage FULL и semantic_ratio SHORT (23.09.2026)

run_portrait_draft.bat CONFIG [--check] поддерживает duration_mode=coverage. В этом режиме target_duration_seconds и max_duration_seconds не задаются; ненулевой лимит отклоняется, а не подменяется огромным числом. Длительность вытекает из раскрытия героя. media_type_policy=equal уравнивает исходные фото/видео, акварели и DE: исторические preferred-оценки ART не являются приоритетом отбора. coverage_map перечисляет грани, примеры кандидатов и пробелы; это не whitelist. Структура обязана вернуть coverage_audit по каждой грани с выбраннымиID или обоснованным пробелом. Каждый кадр остаётся содержательно компактным. Полнота не означает все материалы, повтор очевидного или длинные паузы.

run_short_portrait.bat CONFIG [--check] поддерживает duration_mode=semantic_ratio и approximate_fraction (например1/3). Доля задаёт мягкий ориентир; квоты60–180 и точного коэффициента нет. SHORT должен быть строго короче своего явно указанного FULL, использовать только его кадры и не расширять их диапазоны/длительности. Отбор сохраняет ключевые качества по карте раскрытия; равномерное ускорение не является сокращением по смыслу. Достаточно готовогоFULL-плана: готовность MP4 и FULL_LOCK не требуются. Пока новый план отсутствует, --check сообщает WAITING_DEPENDENCY и не подставляет прежнюю версию.

Это опции конкретной задачи. Старые compact-конфиги и их результаты не переводятся автоматически в новые режимы. Для сравнения вариантов задавать отдельные output_root. Кэш структуры и готового MP4 сохраняется; прерванный рендер может заново собрать сегменты в новом каталоге. Неопределённый API-запрос блокирует автоматический платный повтор. --check не вызываетAPI и не рендерит. Художественный просмотр остаётся отдельным этапом; отсутствие документальных сцен нельзя скрывать метафорами.
