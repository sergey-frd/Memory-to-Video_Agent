# Выбор портрета и воспроизводимый запуск

Пользователь выбирает цель зрительского впечатления. Это альтернативы, а не обязательная цепочка производства всех вариантов.

| Цель | Монтажный принцип | Критерий результата |
| --- | --- | --- |
| Художественный акцент | Сильные акварели и двойные экспозиции как самостоятельные образы; оригиналы там, где выразительнее | Каждый ART раскрывает характер или выполняет переход; нет механических дублей |
| Полнота | Разные подтверждённые грани жизни без квоты хронометража | Новая сцена добавляет грань; отдельные эпизоды не растягиваются |
| Интеграция | Единый монтаж из лучших решений, фото/видео/ART равноправны по смыслу | Цельная драматургия вместо соединения двух готовых фильмов подряд |
| Альтернативный взгляд | Другой вход, порядок блоков, кульминация, ритм и финал | Самостоятельный опыт, а не несколько переставленных сцен |

Рекомендуемый маршрут для широкого семейного портрета: интегрированная основа, затем по результатам просмотра — расширение новыми гранями и/или самостоятельная Alternative SHORT. Пользователь выбирает каждый переход; создавать все варианты заранее не нужно. Если цель сразу ясна, начинать с неё.

FULL/SHORT выбирается отдельно. Расширение принятой основы сохраняет все её сцены, длительности и относительный порядок. Alternative SHORT может заново выбирать материал из каталога, раскрывает несколько выразительных характеристик и остаётся существенно компактнее полной. Точная квота времени не обязательна. Биографические пробелы фиксируются; художественные метафоры не доказывают события или родство.

Готовые JSON-шаблоны: [examples/portrait](../examples/portrait/README.md).

## Исполнители и JSON: текущее состояние

Команды выполняются из `source/` публичного репозитория. Все примеры требуют собственных доступных материалов и новых выходных каталогов.

| Задача | Скрипт / входной JSON | Статус |
| --- | --- | --- |
| FULL compact/coverage | `tools/run_portrait_draft.py --config full.json --check` | Реализовано; обычный запуск без --check может обращаться к платному API и рендерить |
| SHORT из одного FULL | `tools/run_short_portrait.py --config short.json --check` | Реализовано; ID ограничены source_edit_plan, это не свободный alternative из каталога |
| Редакторские integrated/expanded/alternative | Точный edit_plan.json, вручную или отдельным редакторским сборщиком | Единого универсального launcher для этих трёх сценариев пока нет |
| Просмотр готового плана | `tools/render_structure_draft.py --config render.json --dry-run` | Реализовано; без --dry-run создаёт MP4 |
| Нативное завершение workflow | `tools/prepare_native_finish.py` и соответствующий конфиг | Существующий маршрут имеет свои зависимости; см. NATIVE_FINISH_RU.md. Не подменяет собой персональные двухсеквенционные сборщики |
| Сборка отдельных FULL/SHORT через JSX | Job → подготовленный JSX → Run Transition Script | Поэтапный производственный подход; перенос конкретного персонального генератора требует адаптации |

Реальные конфиги FULL/SHORT, поддерживаемые значения и ограничения: [PORTRAIT_MODES_RU.md](PORTRAIT_MODES_RU.md).

Минимальный JSON для просмотра уже проверенного плана:

```json
{
  "schema_version": 1,
  "edit_plan": "edit_plan.json",
  "output_root": "output/new_portrait_preview",
  "width": 1280,
  "height": 720,
  "fps": 25,
  "video_bitrate": "1800k",
  "audio_bitrate": "128k"
}
```

Сохранить как `render.json`. Для однозначного разрешения путей предпочтительны абсолютные локальные пути; правила конкретного исполнителя имеют приоритет. Проверка `python -B tools/render_structure_draft.py --config render.json --dry-run` не выполняет рендер; реальный запуск разрешается отдельно.

## Что сохранять для воспроизведения

- Запрос, выбранный сценарий, родительские планы и причины каждого эпизода.
- Классифицированный каталог, source→ART связи, исходные пути и SHA256.
- Edit plan: fps, целые frames, timeline_start_frame, source IN/OUT, итоговая длительность.
- Конфигурации каждого исполнителя, точные команды, копии использованных скриптов и версия зависимостей.
- Для Premiere: отдельная рабочая копия, job, JSX, профили Motion, подтверждения, журналы и readback.
- Резервные копии до запуска/после приёмки, финальные пользовательские проекты и MP4 с их зависимостями.

JSON задания и JSX не обязательно связаны динамически. Если job встроен в `var job`, изменение JSON рядом не меняет JSX: нужна повторная генерация в новом пакете и сравнение встроенного job с JSON. Render config, hero config, native job и state — разные контракты.

## Нативный этап и контроль

Полноразмерные источники и Motion реализуют выбранный монтаж, не меняя драматургию. PNG для совместимости создаются без уменьшения с учётом EXIF; нельзя обещать сохранение HDR после RGB-декода. 4K-секвенция не создаёт отсутствующей детализации.

Проверенная схема движения: редактируемый Scale, плавный smoothstep, push/pull/частичный возврат; амплитуда выбирается по материалу, лица и жесты проверяются на пике. ASSEMBLY — техническая копия без анимации, MOTION — контрольная копия с ключами; смотреть нужно итоговую секвенцию. Дополнительные цвет, музыка, переходы и экспорт выполняются только по заданию.

Офлайн-подготовка → подтверждение открытия Premiere → один запуск SHORT → журнал и сохранённый проект → приёмка → отдельный FULL → проверка неизменности SHORT → остановка. Если панель недоступна для агента, пользователь запускает один указанный JSX; не повторять автоматически после неопределённого тайм-аута. Монитор не доказывает прогресс Premiere, а блокирующий нативный вызов может не прерваться по таймеру.

PREPARED, SAVED, STRUCTURAL_PASS и USER_ACCEPTED — разные состояния. Ручные изменения после readback требуют нового сравнения; исторический PASS не относится автоматически к текущей копии. Отчёт сообщает измеренное время, ошибки и оставшийся визуальный просмотр, не объявляет рендер выполненным по факту сохранения проекта.

## Будущая формализация — ещё не API

Нужен общий конфиг, который отдельно описывает editorial_intent, format, foundation_plan, catalog, preservation, selection_scope, narrative, selection, output_root и execution. Это проект интерфейса: текущие launchers не принимают эти новые поля как реализованные режимы. Из персональных сборщиков следует вынести пути и редакторские выборы в JSON; сохранить проверки уникальности ID, хешей, кадров, диапазонов, неизменной основы и раздельных подтверждений. Не создавать видимость автоматизированной художественной оценки там, где решение остаётся редакторским.
